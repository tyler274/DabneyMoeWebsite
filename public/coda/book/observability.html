Coda Rust

Observability

The observability stack has selectable operations destinations (traces, logs, metrics, alerts) and Langfuse for agent runs. Destinations are Datadog (APM, logs, Error Tracking, monitors), a self-hosted Grafana stack (Tempo, Loki, Prometheus, Grafana). Both use the same OpenTelemetry trace. The operations backend gets every span with agent content removed. Langfuse gets only model generations, in the hosted project at https://hipaa.cloud.langfuse.com, which Langfuse’s BAA covers. The collector strips content from the operations pipelines unconditionally, so no content depends on an operations vendor’s BAA scope.

This page describes configuration and verification, not live deployment status. Infrastructure, Datadog and Grafana changes require separately authorized, reviewed plans; the observability operator owns their application.

Choosing a backend

datadog is the compatibility default. both runs Datadog and Grafana concurrently with independent bounded exporter queues. Datadog owns operational notifications; Grafana rules evaluate in shadow mode without service paging. See concurrent qualification for the default-off compatibility metrics source, separately gated synthetic notification route, storage review and rollback requirements.

The choice lives in three places that must agree:

  • Collector. One backend overlay, collector.datadog.yaml, collector.grafana.yaml or collector.both.yaml, is merged last and sets only the exporters of the traces/ops and logs/ops pipelines. Without an overlay those pipelines export to nop, so a missing choice drops data rather than sending it somewhere unintended. The privacy and caller processors are the same for both.
  • Services. CODA_TELEMETRY_BACKEND (datadog, grafana or both) only changes the correlation keys in JSON log lines. OTLP export is identical.
  • Infrastructure. telemetry_backend in both observability and rust-environments. The first deploys the Datadog Agent and monitors or the Grafana stack and picks the collector overlay; the second sets CODA_TELEMETRY_BACKEND on the product containers. The switch procedure is in the root’s README. telemetry_content works the same way: both roots set it, rust-environments puts it on the product containers as CODA_TELEMETRY_CONTENT, and observability refuses full without Langfuse.

Locally, services export straight to the compose collector (dev/observability/collector.yaml plus the debug, Datadog or Grafana overlay) with no sidecar or gateway.

Langfuse can be switched off on its own (no langfuse_host in infra/gcp/observability). The gateway then merges collector.gke-no-langfuse.yaml before the backend overlay, and traces/langfuse ends in nop. The ops pipelines and every privacy and caller step are unchanged.

Per signal:

  • Traces. Every span goes to the operations backend (Datadog APM or Tempo) with content deleted. Generation spans also go, with content as the service sent it, to the Langfuse project at langfuse_host.
  • Logs. Services emit their log events as OTLP log records over the same sidecar path. Every HTTP response emits one info record with status, latency_ms and the request’s trace id, and every finished worker attempt emits one info record (physician.worker.attempt_finished) with coda.job, coda.outcome, coda.run_id and the attempt’s trace id, so a request or worker attempt with a span and no log record means the log path is broken. The gateway deletes the same content keys from log record and resource attributes and sends them to the operations backend only (Datadog Logs or Loki); log records never go to Langfuse. Loki indexes only service.name and deployment.environment as labels (service_name, deployment_environment); trace_id, coda.run_id and the other attributes are structured metadata. Cloud Run’s own stdout capture stays in Cloud Logging, so a service with export off still has its logs there.
  • Metrics. Under datadog, request rate, error rate and latency per service come from APM’s trace metrics. Under grafana, Tempo’s metrics-generator derives span metrics (traces_spanmetrics_calls_total, traces_spanmetrics_latency_bucket) and a service graph and remote-writes them to Prometheus. Their only extra dimensions are coda.job, gen_ai.system and deployment.environment; run ids never become metric labels. Cloud Run and GKE platform metrics (instances, cold starts, container CPU and memory, requests answered before the product container) are optional under either backend and off by default: the Datadog GCP integration (datadog_gcp_integration_enabled), which Datadog reads by impersonating a read-only service account, or Grafana’s Cloud Monitoring datasource (grafana_cloud_monitoring_enabled), which reads through Workload Identity as a roles/monitoring.viewer service account. Neither has a key.
  • Release. DD_ENV comes from OpenTofu (staging) under both backends; it becomes deployment.environment. DD_VERSION is baked into each image at build time from its source revision, so a revision’s spans and logs name the image that produced them and no apply can revert it.

The infra/gcp/observability README details the gateway’s transport, authentication and rotation.

  • Spans. crates/telemetry installs one tracing subscriber. When OTEL_EXPORTER_OTLP_ENDPOINT is set, it exports OTLP/HTTP spans with service.name, deployment.environment (DD_ENV), and service.version (DD_VERSION). http_layer traces each request and continues an inbound W3C traceparent.
  • Generations. telemetry::genai::generation_span opens a gen_ai.generation span in Langfuse’s OTel mapping (langfuse.observation.type=generation, gen_ai.system, gen_ai.request.model, gen_ai.usage.*). It also carries the run contract: coda.run_id, coda.job, coda.recipe_version, coda.origin (simulation or real, also written to langfuse.environment), coda.scenario_id, langfuse.session.id, and langfuse.trace.tags.
  • Logs. When an OTLP endpoint is set (or CODA_LOG_FORMAT=json), stdout logs are JSON lines with the W3C hex trace_id and span_id. Under CODA_TELEMETRY_BACKEND=datadog they also carry dd.trace_id, dd.span_id, dd.service, dd.env and dd.version; under grafana they carry no dd.* keys. Exported log records carry the trace and span ids under both, so a Datadog log or a Loki line opens its trace. A log event carries its own fields, never span fields, so content recorded on a generation span never reaches log storage.

Sidecar lifecycle and outages

The sidecar is a second container in each Cloud Run service. The product container does not depend on it: Cloud Run starts and health-checks the product on its own probes, and the sidecar has its own startup probe on the collector’s health_check port with 1 vCPU and 256 MiB limits. Startup order is independent, but revision readiness is not: a collector image-pull or startup failure can prevent the new revision from serving.

  • Gateway or backend outage. The sidecar keeps a bounded in-memory queue and retries for a bounded time, then drops. The product never blocks on export, and its requests keep succeeding.
  • Sidecar crash. The product’s exporter fails fast against localhost and drops; Cloud Run restarts the sidecar. Telemetry from that window is lost.
  • CPU and shutdown. Enabling observability disables CPU throttling for the product and sidecar so export can drain between requests. Both containers receive 1 vCPU, increasing per-instance allocation and billing. This cost belongs in the reviewed deployment plan. On scale-in, the product makes a bounded flush through TelemetryGuard and the sidecar flushes on SIGTERM within Cloud Run’s 10-second grace period; remaining queued telemetry is lost.

Working-window timing

The shared harness retains the opening time in Unix milliseconds on each WindowOpened event, alongside its reason and optional note reference. ProviderStarted retains the request’s admission time. Products store both in their existing run journals. These wall-clock timestamps let inspection relate a window opening to surrounding requests without a second timing store. Cross-process comparisons depend on the hosts’ clock synchronization. The records contain model context and stay with the product; they are not exported to Datadog as raw logs.

Downtime notification qualification

Datadog is the primary staging operational route to #engineering-observability. An independent Cloud Monitoring watchdog covers missing monitoring/probe heartbeat outside GKE. Concurrent Grafana service alerts must stay shadow-only; its contact/evaluator qualification uses a separately labeled test route, not duplicate operational pages.

The local qualification rehearsal prints bounded synthetic failure/recovery, reminder, grouping and maintenance steps and checks timestamped observations without making any external calls. It extends the existing collector/sink tooling but does not substitute a local webhook acknowledgment for a Slack receipt or a fixture for an actual evaluator.

Before live work, read back the exact account/contact/channel mapping and the synthetic evaluator’s signal selector and windows. Obtain explicit approval for the labeled routing send, bounded synthetic failure/recovery and maintenance window, and independent watchdog heartbeat-loss exercise. Include source and deployed revisions, UTC start/end, maximum sends, dedicated target, abort and cleanup steps. Infrastructure changes require their own reviewed saved plan and authorization; approval for a Slack drill does not authorize an apply or IAM change. Restore synthetic healthy signals and end only the drill’s mutes at timeout or abort, verify evaluator recovery, and retain evidence even when delivery fails.

Capture original signal, evaluator Pending/Firing (where exposed), provider notification, human-confirmed Slack alert, evaluator recovery and Slack recovery times. Record provider last_notified separately from the user’s confirmed Slack message timestamp/permalink. Measure detection and delivery intervals with actual ingestion/evaluation delays. Prove absence of duplicate service paging, maintenance silence and expiry behavior, and the independent watchdog route. No downtime-to-Slack claim is valid until those live artifacts are inspected.

Qualification and incident ownership

Datadog owns primary staging service notifications to the confirmed #engineering-observability integration. Grafana evaluates service rules in shadow mode; only the separately authorized, exactly labeled synthetic test can notify. Cloud Monitoring owns the independent probe-heartbeat absence path outside GKE and Grafana. Its heartbeat demonstrates probe execution and direct publication, not collector health or clinical workflow success.

The product on-call owner handles service and overdue-work symptoms. The runtime infrastructure operator handles probe authentication, scheduler execution and state publication; the observability operator handles collection, backend freshness, routing and storage. Use the affected service/environment and stable resource identity in the alert, never patient, conversation or run IDs as metric labels. Correlate a run only in the authorized trace/log investigation surface.

  1. For readiness alerts, inspect the probe’s fixed outcome and freshness first. Authentication failure or login redirect is not application success. Check IAP audience and caller grants without exposing tokens; do not bypass IAP or internal worker ingress to make a probe green. To check reachability on demand, run workspace-tools observability-drill probe --output-dir DIR. It executes one probe slot as the probe identity, the only rehearsal caller IAP admits, and fails unless every target’s readiness sample and the heartbeat read back as successful. A workstation identity token carries gcloud’s own audience, so IAP answers it with 401 by design.
  2. For physician work, read the worker’s queue gauges. Each physician-worker instance writes them every minute from the Postgres rows that own the work, on the global resource and labelled only with its instance id: custom.googleapis.com/coda/physician/queue/oldest_due_seconds (how long the longest-waiting due turn or reply revision has been runnable), .../due (how many are runnable now) and .../failed (how many ended failed and wait for the physician’s Try again). worker_oldest_due alerts when due work has waited past 300 seconds throughout five minutes, and its absence means no worker is reporting; worker_due alerts when due work persists for 30 minutes; worker_failed alerts on any failed work. Datadog imports these gauges only with datadog_gcp_global_location_enabled; Grafana Cloud reads them from Cloud Monitoring directly. Compare them with the worker processing/retry contract and the attempts saved on the rows before acting; do not retry work automatically. Investigate Redis using the configured exact resource scope and the cloud console.
  3. For Cloud SQL, each alert names its instance: physician_* is rust-physician, duet_* is rust-duet. Start from the instance’s overview and Query insights in the cloud console.
    • *_sql_up: Cloud SQL itself reports the instance down for five minutes. Check its operations log for maintenance, a restart or a failover before touching the services that use it.
    • *_sql_cpu and *_sql_memory: the fraction stayed above 0.9 for 15 minutes. The staging tier is shared-core, so a long query, a vacuum or a backlog of worker turns can hold it there; find the statement in Query insights first, and resize the tier only for sustained load the product should carry.
    • *_sql_connections: open backends across the instance’s databases stayed above 80 of its max_connections of 100 for 15 minutes. New connections fail at 100. Compare each service’s pool size and instance count with the limit, and look for connections left idle in a transaction.
    • *_sql_storage: the disk is more than 85% full. Look for unexpected table growth before raising the disk size.
    • *_sql_up telemetry absent: Datadog stopped receiving the instance’s metrics. That is monitoring loss, not an outage; check the GCP integration’s permissions and namespace settings, and the instance’s state in the console, before acting on the database. The instance’s other SQL monitors raise no absence alert of their own, so the loss pages once; an alert of theirs already firing keeps its state and reminders until its data returns.
  4. For missing telemetry, inspect Cloud Scheduler/job execution and the direct Monitoring series separately from collector availability, exporter failures, queues and Datadog ingestion. Keep heartbeat absence distinct from a failing target. A cleared sparse counter or retired pod is not confirmed recovery.
  5. For Grafana/collector loss or storage pressure, inspect stable workload readiness, restart/OOM evidence and mounted PVC used/capacity series. Do not resize from host-memory percentage alone or retain stale node groups as current workload failures. Use the private stack access procedure and provisioned dashboards; preserve IAP and private access.

Follow the infrastructure README’s maintenance and rollback procedure for scoped, expiring mutes and reviewed saved-plan rollback. Keep the independent watchdog active during collector or Grafana maintenance. Image-only releases must preserve sidecars, environment, IAM and networking; an ordinary release’s before/after assertion is part of qualification, not an infrastructure override.

Periodic qualification and every material monitoring change need revision-bound proof. Local mock plans, synthetic OTLP, isolated Grafana evaluation and offline receipt validation prove regression contracts only. They do not prove cloud IAM/token handling, Datadog query/ingestion, real Slack delivery, real dependency failure, deployed volume retention or production evaluation delay. Record those as separate gates and label each exercise simulated signal or actual component failure. An authorized live drill must capture signal → pending → firing → exact Slack receipt → recovery with UTC timestamps and cleanup, plus the independent monitoring-loss route. Do not claim downtime notification readiness until those observations exist. Production is outside this procedure.

From alert to run

  1. Open the primary Datadog notification from the confirmed alert_notify destination. Grafana evaluates equivalent operational rules in shadow mode; it does not send service notifications. Both evaluate the same four alerts (service 5xx rate, service p95 latency, physician chat generation errors, asynchronous failures) with the same thresholds. Check the environment, service, release version and incident time window. HTTP failures and latency cover service requests; asynchronous worker failures need a separate signal because the originating request can already have succeeded.
  2. Follow the error log’s trace link. The worker attempt and generation spans carry canonical correlation; a broker message ID identifies a delivery, not an attempt. Copy coda.run_id, coda.work_id, any predecessor ID, and the trace ID. Preserve the query window and release version with the evidence. Under grafana, reach Grafana with kubectl -n observability port-forward svc/grafana 3000 and use Explore over the alert’s window:
    • Loki to Tempo. Query the failing service, for example {service_name="physician-worker"} | severity_number >= 17. Expand the line and follow its trace_id field’s “Open trace” link into Tempo.
    • By run. {service_name="physician-worker"} | coda_run_id="<run id>" finds a run’s log lines that carry it (Loki turns dots in attribute names into underscores); in Tempo, TraceQL { span.coda.run_id = "<run id>" } finds its spans.
    • Tempo to Loki. From a span, “Logs for this span” queries Loki on the same service and trace_id.
    • Rates and latency. Prometheus traces_spanmetrics_* series by service; exemplars open the matching traces.
  3. An authorized product operator reads back the matching persisted attempt from physician Postgres, scoped to the intended practice and physician. Chat attempts are in the state.attempts collection of physician_runtime_conversations; current reply-revision attempts are in physician_runtime_reply_drafts, and earlier accepted revisions are archived in physician_runtime_reply_revisions. Match the exact attempt ID, its work and any persisted predecessor relationship, and its terminal status. Project only those operational fields into the evidence: do not export the surrounding conversation, chart, instructions or model records to Datadog or Grafana. Never use a retry’s newer attempt as proof for the originally alerted attempt.
  4. In Langfuse (https://hipaa.cloud.langfuse.com), find the generation with the same trace ID and coda.run_id. A trace may contain several attempts, so verify both identifiers. The environment is coda.origin, and tags include coda.job. Input/output exists only when content capture was explicitly enabled; absent content is expected under the default policy. A failure before a model call must not be presented as a completed model generation.
  5. Restore healthy operation and confirm recovery at the notification destination. Retain the notification, trace/log query, scoped attempt readback and Langfuse observation against the tested release. Collector configuration or an empty vendor search is not evidence of delivery or privacy.

workspace-tools observability-drill langfuse alert-to-run walks steps 2 and 4 on a rehearsal turn it sends itself. The chat snapshot names the attempt that answered (runs holds the run once a turn is answered, held or failed, and an answered run’s attempt_id names the attempt); the drill finds that attempt’s span in Datadog by coda.run_id, reads its trace’s generation span, then the Langfuse trace, and fails unless the attempt id and the trace id (Datadog’s 64-bit id is the low half of the 128-bit one) agree across all four.

Langfuse drills

Staging physician chat sends its generations to Langfuse with content, because its rehearsal traffic is synthetic. workspace-tools observability-drill langfuse proves that on the deployed stack, one action per run, each writing langfuse-<action>-<UTC stamp>.json with the deployed revisions it ran against:

ActionWhat must hold
rehearseA canary turn sent as the rehearsal physician answers, and Langfuse holds its generation in environment simulation, with the scenario, the chat as session, coda.run_id, a 128-bit trace id and the canary in its input or output.
alert-to-runThe same turn found from Datadog: the snapshot’s attempt id, the attempt span, the generation span and Langfuse agree on coda.run_id and the trace id, and the attempt span records coda.trace_relation link: the attempt started its own trace linked to the request that accepted the turn.
isolationLangfuse holds the canary (the positive control) under the snapshot’s attempt; the operations spans of the same trace exist in Datadog, and in Tempo under grafana, with model and usage, and no canary anywhere; Datadog Logs, and Loki under grafana, hold the physician logs of the same trace (their positive control) and no physician log event since the turn carries the canary in any field.
chat-failureThe physician chat failure monitor is OK, then the drill sends one more canary turn than its threshold, each marked [fail:1]. Every turn answers on a retry and the monitor fires. For one turn, the answering attempt’s span names the failed attempt as its predecessor in the same coda.work_id; the failed attempt’s span has error.type rehearsed; the monitor’s own query, narrowed to that attempt, finds the error generation in the failed attempt’s trace; and Langfuse holds that attempt’s generation in the same trace at level ERROR, with the canary. Both attempts’ spans record coda.trace_relation link to the accepting request. Datadog holds no canary in either attempt’s trace, and the monitor recovers after its 10-minute window.

The rehearsal physician is the physician-rehearsal service account. Its turns belong to a practice in physician_simulation_practices (rust-environments), so the worker labels them simulation; a turn in any other practice stays real whatever it sends. The operator signs in with gcloud as one of physician_rehearsal_signers, which may mint the account’s IAP token through IAM signJwt; POST /auth/rehearsal then admits exactly that principal. Every kubectl call names the staging context gke_coda-rust-staging_us-east1_rust-observability, so an ambient context is never used; the drill opens its own port-forwards to Tempo and Loki, reads Langfuse at LANGFUSE_BASE_URL with the project keys, and reads those and the Datadog keys from Doppler coda-rust/stg without printing them. Every receipt records the Langfuse origin it read as langfuse_host.

Every wait runs under the exercise’s 40-minute cap and the operator’s Ctrl-C. A readback request that times out or cannot connect, as a port-forward may, counts as one of the wait’s polls; an error status or a malformed answer ends the run at once, and a wait whose every poll failed reports the last failure. The Langfuse export monitors in langfuse-monitors.tf, behind langfuse_monitors_enabled, page when the collector cannot deliver to the hosted project; no drill takes the hosted project down to fire them.

chat-failure pages #engineering-observability, so it needs --confirm, and runs only with the operator’s approval for that window. Its failure is the worker’s own: a rehearsal turn marked [fail:K] fails its first K attempts before any model call, with error.type rehearsed, and the worker runs it again once its retry backoff is due. Only a practice in physician_simulation_practices on the staging-preview profile honours the marker; a real practice’s turn answers whatever it says. The monitor is chat_generation_errors in datadog.tf, on in staging through chat_failure_monitor_enabled while the other service monitors stay off. The drill writes its own exercise, group staging/physician-chat-failure, to the same observations-langfuse-<stamp>.json ledger: the first marked turn, the monitor’s firing, the restore right after it (every marked turn has answered by then, so the failures have stopped), and the monitor’s recovery; a person adds the Slack alert and recovery.

Validation

The observability job in CI validates, inside nix develop .#observability, the collector and OpenTofu shell, the base collector alone; the base with each local overlay (debug, Datadog, Grafana); the authenticated GKE gateway with each backend, with and without Langfuse; and the inline sidecar. It checks the compose file with each profile, verifies the Tempo, Loki and Prometheus configs with their pinned images, and validates and runs mocked OpenTofu tests for both observability and rust-environments. Backend-free initialization belongs in a fresh test checkout, never over an operator’s initialized backend.

Run the synthetic collector behavior test separately:

nix develop .#agent --command python scripts/test_collector_privacy.py          # both backends
nix develop .#agent --command python scripts/test_collector_privacy.py grafana  # one backend

It runs the production file order with the datadog or grafana overlay last and exercises content stripping with positive controls, authenticated caller filtering, and bounded queues during exporter outages. The generated evidence under target/verification is local proof, not evidence of deployed delivery.

The Grafana alert rules fix their thresholds in dev/observability/grafana/provisioning/alerting/rules.yaml, because Grafana provisioning has no defaults for unset variables. A precondition in infra/gcp/observability fails the plan under grafana unless they equal the threshold variables the Datadog monitors use, so change both together.
