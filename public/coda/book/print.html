Canonical evidence ingestion

EvidenceStore is the single mutation owner for canonical health evidence and clinical notes. It applies single and batch mutations under an account-locked transaction. The HTTP routes POST /api/canonical-evidence and POST /api/canonical-evidence/batch always write with device authority. Device authority may not create, correct, revive or remove the originals of the server-owned portal sources (epic, oracleHealth, healow, googleHealth). Those originals can be written only in process, through ingest_with_authority and a matching connector source kind and connection. Such refusals return the stable conflict code source_authority_refused. A record’s source kind, connection and note label are fixed when it is created.

  • A batch holds 1–100 items, each a bounded source object up to 2 MB. Each item runs in its own savepoint and gets an accepted or typed rejected outcome, so no item is skipped silently. An infrastructure failure aborts the whole batch.
  • Retrying an operation returns its first acknowledged address. A new operation identity must name the exact current revision.
  • measured_at or recorded_at is stored only from an RFC 3339 instant the source declared. Otherwise the stored date is unknown (NULL); receipt time is never used, and the literal stays in the payload. Patient-authored notes (Added in Duet) must carry an explicit instant.
  • operation: "delete" is an explicit removal by the owning source, fenced by exact revision and source generation. It keeps the base row and retained revisions, marks membership deleted and source_removed, and leaves earlier revisions readable as non-current citations. Privacy erasure (privacy recovery) deletes base rows and their retained revisions, and remains authoritative.

Persistence and migrations

The API never owns schema migration at startup. Run duet-migrate with DUET_MIGRATION_DATABASE_URL and DUET_RUNTIME_ROLE. The migration role and pre-existing runtime login must be distinct; the runtime role must not be a superuser, bypass RLS, create roles/databases, or inherit the migration role. The binary applies the Duet-owned chain first and optionally the front-door chain when FRONT_DOOR_DATABASE_URL is supplied. Do not replay the coda-app migration ledger to initialize this service.

Queries go through the typed database API, as AGENTS.md asks. Schema/account transactions use SQLx. src/sql/has_migration.sql is a schema-readiness query, not a CRUD pattern, and duet-migrate keeps the separate reference schema_migrations ledger. Ordinary CRUD belongs to the owning product’s typed entities; products do not share stores.

Isolated restore qualification

A database restore and a privacy replay are separate gates. Keep the restored Duet database disconnected from serving, subscriptions and outbound effects until both have passed. The operator selects a successful backup and retains the independent journal through the recovery cutoff; restoring the journal to the SQL backup’s timestamp would discard restrictions accepted after that backup.

duet-privacy-replay with no receipt arguments calls the product’s full reconcile_inventory path. Passing selected receipt IDs is targeted repair, not full restore qualification. Hosted replay requires the independent GCS journal and its authorized attached identity. An empty replacement bucket or a SQL-derived list cannot establish coverage of the independent inventory. Establish its provenance and completeness separately.

A synthetic rehearsal must retain a backup containing an account and its data, then record deletion or withdrawal in the independent journal. Restore the older SQL into an isolated target and replay the newer inventory. Check the stored restriction and refusal through the product owner, including repeat replay and missing-journal refusal, before any claim that deleted data cannot return. The physician database has its own schema, principals and readback checks; it does not import Duet’s privacy types.

GCP recovery owns disposable cloud targets and operator approval. Record backup identity, target, replay evidence and validation results together. A successful SQL restore operation, a local file-journal test or a ready process alone does not qualify hosted recovery.

Runtime schema cutover

The harness cutover changes the shape of the Chords runtime tables. It is a clean cutover: nothing reads earlier runtime data, so these tables are reset once. Rust staging holds only synthetic physician runtime data. Ordinary releases never reset data, and neither startup nor Store::migrate performs this reset.

This section states what the cutover needs. How staging stops writers, reaches the database, releases images and routes traffic is the infrastructure owner’s procedure and is not described here.

Before the site and the worker start, the settings in Model settings exist for both. Each refuses to start without them.

The reset discards chats, drafts, revision history, response feedback, attempts, command receipts, frozen execution inputs, provider cooldown, retained synthetic chart observations, practice source access, shared source adapter state, and patient source links and pull status. It also drops physician_runtime_migrations, the runtime chain’s ledger, so a reset leaves no ledger behind. It leaves account, session, practice, panel and front-door tables in place.

After the drop:

  • The synthetic charts are loaded again with physician-migrate load-charts, because the reset drops the source tables that hold them. See Staging synthetic charts.

An automatic deploy of the cutover commit does not perform the reset. If the reset is skipped, the runtime migration fails: its first migration creates each runtime table and stops at the first one that already exists. It runs in one transaction, so it leaves the runtime tables as they were. The physician-migrate job then fails, and the release stops at that failed migration.

runtime.sql is the first migration of the runtime chain. The chain records each applied migration in physician_runtime_migrations, like the physician-auth, front-door and clinical-library chains, and Store::migrate applies only the migrations not recorded there. A later schema change is a new migration in the chain. Existing permanent records are not rewritten to add fields. Once a practice holds real data, storage changes must neither refuse to start nor wipe it, as the physician intent requires.

Physician sign-in and practice access

physician-auth is one durable owner for who a clinic user or physician is, which practice they belong to, who holds panel-assignment permission, and which patients are on each physician’s panel. Sign-in is a per-user email magic token: the server issues a one-time token (24-hour TTL, stored sha256-hashed), and its verification mints one bearer session (idle for 12 hours, and never past 7 days after sign-in) with a revocation fence (sessions_ended_before) so deactivating an account ends every session it holds.

Access follows three concentric boundaries:

  1. Practice boundary (cross-clinic isolation): Any patient or workspace outside the signed-in user’s practice_id answers 404 — never 403 — and never appears in roster search.
  2. Clinic demographic boundary (same clinic, not on the physician’s panel): Physicians and staff in the clinic can search the clinic’s patient roster and read basic demographic information (display_name, birth_date, age_years, sex_or_gender, medical_record_numbers) on GET /patient-workspaces/{id} for other patients in their clinic, while clinical synopses, citations, chats, follow-ups, Today items, drafts, and commands remain omitted/404.
  3. Panel clinical boundary (Membership::Allowed): Full clinical workspace reads, Today items, chat snapshots, drafts, and commands require the patient to be assigned to the physician’s panel. Clinic admins, secretaries, and physicians holding the admin permission can assign or remove clinic patients on a physician’s panel via PUT /auth/panels/{physician_id}/{patient_workspace_id} (AuthStore::assign_panel).

The store is the AuthStore trait over SeaORM and PostgreSQL: physician-sample holds Arc<dyn AuthStore> and picks the Postgres store (connecting without applying migrations; the migration job owns schema changes) when PHYSICIAN_DATABASE_URL is set, process memory otherwise. Practice creation and physician account management

Coda staff create practices and manage physician accounts through the dedicated staff setup surface (/auth/staff/* in staff_setup.rs), separate from the staging migration seed (PHYSICIAN_STAGING_ACCOUNTS) and the automated IAP rehearsal route (POST /auth/rehearsal). The routes exist only when PHYSICIAN_AUTH=required and CODA_STAFF_SETUP_TOKEN holds a secret of at least 16 bytes; when unset, /auth/staff/* answers 404, and missing or non-matching bearer headers fail closed with 401 after constant-time SHA-256 comparison (StaffSetupAuth in hosting.rs).

Each staff call sends Authorization: Bearer <CODA_STAFF_SETUP_TOKEN> against the hosted Chords origin:

  1. Create or verify the practice and its time zone: PUT /auth/staff/practices/{practice_id} with {"clock": {"mode": "real_time"}, "time_zone": "America/New_York"} (or {"clock": {"mode": "fixed", "unix_seconds": 1787846400}, "time_zone": "America/New_York"} for a synthetic practice). PracticeTimeZone validates the IANA identifier against the bundled time zone database before saving physician_practices, returning 201 Created on first creation, 200 OK when an existing practice matches (clock, time_zone), 409 Conflict when an existing practice holds a different clock or time zone, and 422 Unprocessable Entity when the time zone or practice identifier is invalid. GET /auth/staff/practices/{practice_id} reads back the saved practice clock, time zone, patient count, and accounts.
  2. Invite a physician: POST /auth/staff/practices/{practice_id}/invitations with {"email": "physician@practice.example", "display_name": "Dr. Example", "role": "admin" | "physician"}. Hosted delivery mails a single-use 14-day sign-in invitation link (https://<origin>/?code=<token>&email=<email>) and omits the token from the HTTP response (502 Bad Gateway if mail delivery fails); local proof mode returns the stored token and sign_in_path. Opening the link redeems the invitation through POST /auth/verify (AuthStore::redeem_invitation), creating the active physician_accounts record and minting a browser session.
  3. Create, deactivate, or reactivate an account: POST /auth/staff/practices/{practice_id}/accounts creates an active physician or practice-admin account directly ({"email": "...", "display_name": "...", "role": "admin" | "physician"}), returning 200 OK only when an existing account in that practice is active and matches both role and display_name (409 Conflict otherwise). POST /auth/staff/practices/{practice_id}/accounts/deactivate ({"email": "..."}) marks active = false, advances sessions_ended_before past every held session, and emits NOTIFY physician_authority so active browser sessions and event streams stop immediately while sign-in is refused, and POST /auth/staff/practices/{practice_id}/accounts/reactivate ({"email": "..."}) restores sign-in without reviving sessions ended by deactivation. Newly created physicians and practice admins start with an empty panel (0 patients) until patients in their practice are registered and assigned, and cross-practice requests return 404.

Each practice’s saved PracticeTimeZone (care.rs ConnectedCare::practice_moment) governs the local calendar date and time_zone returned on GET /practice-day, GET /today, GET /updates, and GET /patient-workspaces/{id}. Practice-scoped clinical source setup, recovery standing, and Spruce backlog state (GET /connections and /connections/{source_id}/* in source_setup.rs) persist in PostgreSQL (physician_practice_source_setups, keyed by (practice_id, source_id)), keeping Connected, RecordsImported, UpToDate, ReadFailed, and AccessLost distinct across server restarts while retaining previously linked chart records and reply drafts. Real-time practices (PracticeClock::RealTime) and production (CODA_ENVIRONMENT=prd) expose Coda-assisted onboarding (CodaAssisted) and answer 404 on /connections/{source_id}/simulate; synthetic fixed-clock practices (PracticeClock::Fixed) outside production additionally expose synthetic walkthroughs and fault simulation for verification.

Scaling across instances

A turn that finishes on one physician-sample instance has to show up on a stream another instance is holding open. physician-bus is the physician product’s fan-out. It carries workspace_changed, workspace_settled, and resync. resync is what a subscriber gets when it lags or the connection drops, and the Dioxus client refetches on that event. Sign-in and panel changes stay on the existing Postgres NOTIFY feed, which also fires for the migration job and for psql.

RedisBus is the fred client: TLS plus AUTH, PHYSICIAN_REDIS_URL as a rediss:// URL and PHYSICIAN_REDIS_CA_PEM as the Memorystore server CA. With PHYSICIAN_REDIS_URL unset, LocalBus keeps those events inside one process. That is the local and test path.

Hosted message.submit accepts the turn in Postgres. The transaction that saves it also sends pg_notify on the channel physician_work with {scope, input_id}, and nothing else. Postgres delivers a notification only when its transaction commits, so there is no accepted turn whose announcement failed. Try again, Resume, an accepted reply revision and a claim a stopping worker hands back are announced the same way (runtime/delivery.rs).

physician-worker holds one LISTEN connection and starts announced work at once (pull.rs). A notification sent while that connection is down is lost, so the worker also reads the due work every 10 seconds, and again each time it resubscribes: pending work whose retry delay has passed, and attempts whose lease ran out. A notification only names work. The claim in Postgres decides who runs it, so work heard twice, or by two workers, runs once, and work that is committed, stopped, replaced by a newer message or held under another live claim is not claimed. A worker runs at most four attempts at a time. Its HTTP listener serves /health and /readyz only; there is no route that delivers work.

When a newer message steers an executing answer, running calls finish within their 300-second deadline before settlement releases the old claim. Stop does not wait for running calls. Settlement makes the waiting message due at once and announces it in the same transaction, so a listening worker starts the answer without waiting for its next due-work read.

The worker publishes workspace_changed after each committed reply and each failed attempt, including a provider that cannot start and a claim that finds the turn already failed, and after each step the physician sees starts or returns, so an open page shows the steps while Coda works. A step’s notice never waits on the bus: the run only marks it pending, and a task of that attempt publishes, folding the notices that arrive during one publish into a single publish after it, so a slow bus neither delays the run nor drops the last step’s notice. A claim that finds the turn already failed is how a turn whose worker leases all ran out ends: the claim records the fifth failure and nothing is left to run. A held page then refetches and shows “Coda couldn’t finish”. Accepted work lives only in Postgres, so a turn accepted by a site instance that died, or announced while no worker was listening, is found by the next due-work read of whichever worker is up. tests/instance_loss.rs proves both against Valkey and Postgres.

An intentional Stop is work.stop. It holds that turn until work.resume or a newer message, including across a worker restart, and the site publishes workspace_changed so another open tab refetches. The snapshot shows Stop while the turn is still pending or active, and Resume once it is held. Each Stop press is its own command, so Stop after Resume holds the resumed run again, even before a worker claims it; each hold names its own run for Resume. Another press on work that is already held is answered as accepted and changes nothing. A newer message releases the hold and is answered, and the stopped run loses its Resume. A late model result cannot publish over Stop or over the newer message. An infrastructure failure does not end the turn by itself: the worker settles it using the harness failure classification, and a crash before that write leaves the attempt leased so expiry starts a successor. A run that marks no step for 600 seconds is recovered the same way: the worker cancels it, stops renewing its lease and settles nothing. The harness owns the five-failure ceiling. Reached limits and intentional interruptions never consume that allowance. At the run limit, the final request may leave a partial answer. Try again continues the work with a fresh allowance. A structured job keeps its handoff in the run record until its own finish operation publishes. tests/stop.rs proves Stop, the held readback after a worker restart, a second Stop after Resume, and one answer to a message sent while held.

Each published reply has a response id: the id its assistant message is saved with in the commit that publishes it, which names the attempt that answered. It stays the same across restarts, so it is the reply’s durable identity, the one feedback and evaluation refer to, and the team matches it to the attempt’s telemetry. Conversation::responses reads the published replies with their ids. A partial answer kept when a run reaches its limit is not a response and has none. The chat snapshot is a typed transcript (physician-wire), built by Conversation::transcript (runtime/transcript.rs): one exchange per piece of accepted work, with the messages that started or steered it, its steps and its answer. A finished answer carries its response_id and the attempt_id that published it, so an operator can match the reply to its telemetry. Each exchange carries in kept every partial answer a limit kept, in order, whatever its answer’s state now: Try again continues after that text, so it stays before the answer that finishes it. A kept partial carries no response id. Each answer keeps the ending its work had, read from that work’s own run history, and only the current work offers Stop, Resume or Try again, naming the run. A step is typed facts from the tool’s arguments and receipt, never a tool name or model prose, and each shown tool has one function from its call and result to a step, next to the tool (physician_chat::step). Skill reads, working notes, result pages and patient memory calls show no step. An exchange’s steps are either read, in the order Coda started them, or unavailable when one of its saved calls cannot be read as a step; that exchange still shows its messages, kept text and answer, the error is logged, and no partial list stands in for everything Coda did. A repeated message.submit under the same key is answered as accepted and runs nothing again; a different command under that key is rejected. Receipts belong to one physician, so another physician’s command under the same key is theirs alone. The session’s practice and physician scope every read and command, and the panel check answers 404 for a workspace the physician cannot see. A colleague with the same patient on their panel reads and changes only their own chats. tests/durable_access.rs proves a repeated submit runs one turn whose reply carries its response id, and that a colleague, an off-panel physician and another practice can neither read the chat nor Stop, Resume or write into it.

The worker listens on PHYSICIAN_WORKER_LISTEN_ADDR when it is set, otherwise on 0.0.0.0:$PORT when PORT is set, otherwise on 127.0.0.1:8791.

Chat acceptance requires durable chat, the database and required sign-in configuration together. A hosted site without durable chat refuses to start; local fixture pages remain display-only.

Reply revision runs in the worker. Drafts live in physician_runtime_reply_drafts, one JSONB row per practice, physician, workspace and reply, which Store::migrate creates from the fixed runtime baseline. GET and PUT /replies/{id} read and save that row; a save must name the current revision, and a PUT never creates a draft. reply.revise checks the session and workspace, then Store::accept_revision records the instruction, the saved text it applies to and the workspace’s current source revisions with their version, read in its own transaction, and the same transaction announces a reply_revision delivery on physician_work. The same command id returns the same acceptance and announces nothing new. A draft that is missing, belongs to another physician, has moved past the command’s expected revision, or already has a revision in progress refuses with 409.

The worker claims the draft and runs revision.rs through the shared harness recovery and execution path with the physician product’s frozen recipe. Revisions offer the shared working-note, fresh-window, history, skill and retained-result paging capabilities. The accepted draft owns its skill package and events; a successor keeps both. Notes are private work records, never saved reply text. History lists and reads this draft’s accepted physician instructions and completed model revisions under current authority. read_patient_sources answers from the attempt’s pinned sources, and only finish_reply_revision can publish the revised draft. Each model exchange is saved before the next one. A retry reuses the same instruction and base text, pins the newest sources when claimed, and restores the request count and usage already spent, so the shared backstops cover the whole revision.

Anything Coda is still working on takes in what arrives before it finishes, so nothing it produces rests on an older reading. A reply under revision is still a draft; its history is fixed only once something is said or sent. Store::commit_revision therefore compares the attempt’s source version with the workspace’s current one in the transaction that would publish, under the draft lock, the auth owner’s locks and a shared lock on the source version row. If they differ, nothing is published. The attempt records a SourceRefresh (from and to version, added, corrected with the earlier revision kept, and withdrawn sources), the draft re-pins, and the model receives a sources_changed result naming those references. It reads them and finishes again in the same run, under the same request bound; a catch-up is not a failed attempt. A finish whose context does not yet hold an exact read of every added or corrected source, at its current revision, gets sources_unread instead. If the chart keeps changing until the bound runs out, the revision stays held with its handoff in the run record and the saved draft is unchanged. The attempt’s sources stays what it claimed and its refreshes show what it could read afterwards, so the record lists only sources Coda could actually read.

Hosted sources live in physician_runtime_sources and physician_runtime_source_versions (runtime/sources.rs). Charts arrive through Store::record_chart and Store::record_chart_with_receipt, which land a patient’s delivery in one transaction, as one version, keeping saved records that a later pull omits and recording their candidate IDs in missing_candidates; explicit withdrawal goes through Store::withdraw_source. A delivery says what the source holds now, so an earlier revision delivered again becomes current. A site also imports the CODA_PHYSICIAN_SOURCE_SNAPSHOT file at startup through Store::import_sources when one is set; a correction or withdrawal is a new row, never a rewrite, and the workspace’s version moves only when what can be read changes. A revision identity is immutable within its workspace and candidate: different content or provenance under an already recorded identity is refused, including after correction or withdrawal. Replaying any identical historical revision is a no-op, so an older instance’s startup snapshot cannot roll back a correction or resurrect a withdrawal. Restoring a withdrawn candidate requires a previously unseen revision identity; opaque revision strings are not sorted to infer age. Catch-up checks compare the exact native content, hash and provenance as well as revision identity, not just a matching revision label. Store::record_source owns individual immutable revisions and is also used by the startup import. Projection prose and model output never become sources. Completion commits under the physician’s current session authority and the draft revision accepted with the command. If the physician saved a newer draft in between, the late completion is refused and their text stays. A failed attempt returns the revision to pending, due again after its retry backoff; the fifth failure ends the revision as failed. The draft GET returns revision_run, the latest accepted command id and its status (pending, active, completed, failed or superseded), so a failed revision is visible, not only stored. Accepting another revision moves the previous one, with its sources and every attempt’s records, into physician_runtime_reply_revisions in the same transaction, one row per earlier revision. The draft row holds only the current revision, so its size does not grow with history. A history row changes only when a superseded attempt’s worker records a late exchange, observation or failure; that record is appended to the archived attempt and cannot publish or alter the current draft. Each row carries a per-draft ordinal assigned under the draft lock, and Store::earlier_revisions reads one physician’s draft oldest first by that ordinal. The worker’s due-work read finds due revisions and expired revision leases just as it does turns.

Skills in physician chat

Chat in physician-worker offers skill_view, working notes, fresh windows, history and result paging, together with search_patient_information, read_patient_sources and the patient memory tools. Discovery searches retained source content, decoded text and metadata within the authorized workspace. A blank query browses records. The model receives references and dates on demand and opens a specific revision for evidence. A changed or withdrawn revision requires a new search. Large reads return exact UTF-8 passages with a continuation into the same revision, including its decoded text. Local developer-plan chart calls are restricted to the synthetic bank. The physician site loads its skill catalog from PHYSICIAN_SKILLS_DIR at startup. A local site defaults to the workspace catalog. Hosted admission requires a packaged catalog. The site saves the package with accepted work so each attempt or replacement worker opens exactly the bodies and resources named in that work’s index.

Each model request carries the physician-owned system prompt followed by the catalog metadata: names, descriptions and resource paths, but no bodies. Then come the skills the job loads at its start, each in full: chat loads patient-record-retrieval, a reply revision loads none. Every Chords job lists the whole package. The accepted work retains that exact package and recipe. The model opens an approved skill by name. An optional file_path opens a registered supporting resource. The exact body is retained; large results use the shared preview and range reader. An unknown tool or malformed arguments come back to the model as {"executed": false, "error": ...} without running; an unknown skill comes back unavailable. An unknown skill name also returns the names of the skills the package has. A bad call does not stop a valid read in the same turn. A skill is guidance only; it grants no tool, patient read or action. The Responses request carries an opaque cache key scoped to the conversation.

Chords uses the shared run budgets. Each work retains one frozen recipe. A provider dispatch references saved items, records its new input or send-time projections and carries the IDs of newly included physician messages. Recovery reconstructs the exact request from those parts; a transport retry records a separate attempt to send it unchanged. New steering or source feedback makes a new request. A large source result stays with the work and can be read in pages.

Chat and revision events are appended to physician_runtime_events, scoped to their product owner and attempt. Status, revision, accepted session and attempt leases use typed control columns. Appending execution evidence does not rewrite authored history; status transitions update their own control state. Readback and recovery join the event rows to their attempts; archiving a revision keeps those same rows, including evidence that arrives late.

The worker streams provider events through the shared Responses adapter. The run record retains usage and completed messages; reply fragments use the live-text callback and Chords neither saves nor displays them. Chords publishes the assembled whole answer. The provider’s silence timeout measures gaps between complete events, so a stream that stops making progress can retry within the run before an answer is published.

Hosted chat supplies its retained authored messages to the harness’s shared history tools. The model can list in either order, search exact text and read a message in character chunks. List and search previews leave the stored originals unchanged; each chunk carries its original message identity, offset and full length. Result paging also applies to history reads, under the same current physician authority.

Chat and reply revisions read and change the patient’s memory through list_patient_memory, read_patient_memory, search_patient_memory, add_patient_memory_note and edit_patient_memory, and both instructions carry the same paragraph on memory. The patient is always the run’s authorized scope. The store sets a note’s time and number, and the run sets its work, its call and the physician message the note comes from: the newest message of a chat’s work, or a revision’s one instruction. The model sets none of them. A note keeps the model’s quote on one line.

The summary, the direction, the person page and each subject page are stored as the markdown text exactly as the model wrote it, one row for each version, and code gives no meaning to the text’s structure. edit_patient_memory names a file by its path and takes a list of edits: create, replace, append and delete. A replace names text that is in the file exactly, in one place, and changes only that text. An edit that cannot apply is left out with its reason, and the others are saved as one new version. A log day is generated from its notes and the rounds marks on every read.

Patient rounds are the regular pass that tidies the summary, the direction and the pages. rounds::run runs one patient’s rounds on the background role with no physician present. It reads memory and the chart with the same read tools and writes with the same edit_patient_memory. A finished run saves a rounds mark. A run that stops early saves none, and what it wrote stays. Nothing schedules rounds: the physician-rounds command runs one patient once, and the code marks with Infra seam: what production must supply around a run.

Memory loads once per conversation. Every request and fresh window of a chat, or of a reply and its revisions, opens with one developer message that Store::memory_at_start builds from the patient’s memory as the conversation started: the summary up to 16,000 characters, cut at a line end; the whole direction; and the whole notes saved since the last finished rounds run started, newest first, up to 8,000 characters. A line names what did not fit and the file that holds it. A patient with no summary, direction or note then gets no message. A chat starts when its first physician message is accepted, and a reply when its first revision is accepted. The memory tables are insert and select only, so the message is read again from rows saved before that second and is the same text each time; no copy is stored. It is the first item, before any earlier conversation, and the instructions stay the same for every patient. Memory saved later reaches the next conversation, and a run reads it with the memory tools.

Model settings

Every enabled Chords runtime requires CODA_<ROLE>_MODEL, CODA_<ROLE>_EFFORT, CODA_<ROLE>_CONTEXT_WINDOW_TOKENS and CODA_<ROLE>_INPUT_LIMIT_TOKENS for CHAT and BACKGROUND. Missing or invalid settings refuse startup. Hosted revisions select the background role. The site freezes each recipe when it accepts the work: model settings, system prompt, tools and skills. Workers read that saved recipe through retries, steers and recovery.

Local process settings and the product’s hosted Doppler configuration own the values. The synthetic stack declares its settings in scripts/physician-scale-stack.py.

The shared token backstop counts output plus input not reported as cached. Missing counts use the existing context and content estimate; recorded provider usage stays distinct from those estimates. Billing belongs to the provider’s usage records. The budget survives recovery through the product’s retained run events.

The working window is separate from the provider input limit. The harness estimates the first request and each fresh window, then uses reported input and output usage plus an estimate for added content. It requests a handoff near its named threshold, reserving room for the reply. Chords sets no output-token cap. Dispatch events retain those counts. When context is full, or the provider refuses it as too long, the harness opens a fresh window from exact accepted inputs and pending results. The fresh window carries the exact text of the newest note saved in this work, says when work done after that note is not in it, and points to earlier notes in the order saved. A refused fresh window gets one retry with smaller pending results, then the run is held at a limit. The shared response transport bound is separate from context pressure.

Large tool results appear as short previews of their start and end. The exact original stays in the product’s run record. read_tool_result reads a byte range or finds a literal match under current authority. Previously sent results stay unchanged within their window, and a partial read never establishes full source coverage. The harness owns presentation bounds; those bounds do not reject writes.

Chords publishes only the answer the model hands in through finish_answer, after checking the saved candidate, current lease, input revision and physician authority. Earlier tool narration stays in the run record. An empty ordinary model turn gets feedback, and so do plain text, a finish beside other calls and a finish without its Basis. citations.rs checks each citation’s label against the versions this work’s reads gave and saves the answer without labels, with each citation’s version, every place its optional quotes occur in the text the model is working from, and the Basis, as the citations spec describes. A description Coda hands in, in its own words, is saved with the finish only for a version the answer or the Basis cites, at most one per version; any other description is dropped and never refuses the finish. At a run limit, Chords keeps the handoff text, without labels, as a partial reply and offers Try again. A revision that reaches its limit stays held with its handoff in the run record. Only its explicit finish operation can update the draft.

Application contract

The application design is Dioxus route components prerendered at startup, served by a stateless axum binary. The sitemap lists only current documents; archived versions stay reachable from their policy pages. /physicians and /api/physician-waitlist are 404.

Startup builds the page/asset tables and their identity, gzip and Brotli representations once; requests do not render Dioxus or query a database. The server serves content-addressed immutable assets and HTML with bounded public/shared-cache lifetimes, encoding-specific ETags, conditional requests and bodyless HEAD responses. Every response carries Strict-Transport-Security: max-age=63072000. Motion is /homepage/site.js on / and /duet. It also paints the landscapes, and the browser proof fails if the hero pointer jumps instead of gliding. The other stylesheets and scripts are layout or fallback only, never motion, and tests/stylesheets.rs holds stage.css and noscript.css to that: stage.css reserves and scales each product frame before the script runs (it then sets the same values inline), noscript.css reveals content when scripts are disabled, and chrome.js floats the nav after 8px of scroll. Reduced motion is decided by site.js at load.

Chords, the physician product, and Duet, the patient product, are presented the same way. The Chords lockup on / introduces the physician product as the Duet lockup introduces the patient one: each product’s mark and wordmark (brand/chords/, brand/duet/) with its audience, in the product lockup styles, through one component (ProductLockup in src/pages/brand.rs). The footer’s link columns are Chords, Duet and Coda Health: each product’s pages under its name, and the company’s contact, privacy policy and terms, which cover the site and both products, under Coda Health.

The Duet story (src/pages/phones.rs) shows Duet on / and /duet as one story across three phones. It reuses site.css phone hardware and the stage scaling and landscapes site.js applies to every frame, but its classes (duet-story, ds-*) are its own, so the phone loop in site.js never binds to it. Its styles are css/duet.css, every selector scoped to .duet-story (tests/stylesheets.rs checks this); its motion is homepage/duet.js, which plays only while the stage is on screen. The markup is the story’s last frame, which reduced-motion and no-script visitors see.

Every page shares chrome.css, which owns the tokens, type, page opening, cards, nav and footer. Pages belong to one of two families (Route::shell) that differ in the stylesheets they load and the layout around their content. / and /duet add site.css, the motion script and the Duet story. Every other page, the legal documents and not-found, adds css/document.css, a hand-written stylesheet with its own reset and named classes for those pages, and sits in the .page layout, which keeps the footer at the foot of a short page. A trailing slash is removed with a 308 that keeps the query.

Static export mode (public-site --export-dir <dir> --base-path <prefix> --origin <url>) renders the same startup pages, 404.html, sitemap.xml, robots.txt, .nojekyll, and hashed/raw assets to disk for subpath hosting such as https://dabney.moe/coda/ or GitHub Pages (with the architecture book and WASM SQLite physician demo built alongside by scripts/build-pages-site.sh with ORIGIN defaulting to https://dabney.moe).

Legal documents are data. Each current document is one record in data/<document>.json holding every word of it: heading, title, intro, date and sections. That covers Duet’s privacy policy, terms and consumer health data policy, Coda Health’s privacy policy and terms, and Clinical Transparency. Each archived version is its own record in data/archive/<document>/<slug>.json, named by its slug, and does not change. Each block of a section’s body is an object with one key naming its kind: paragraph, linked, list, table or source. src/legal.rs types and loads the records, listing each archive’s versions newest first, and src/pages/legal.rs renders them. Startup stops, naming the file and the fault, when a record has a missing, renamed or repeated field or a link that isn’t one of the site’s pages. Legal pages’ titles and descriptions are in src/route.rs, with every other page’s. Legal wording changes with its normal legal review.

Staging applies its origin IAP gate to pages, assets, redirects, health routes and errors. Responses force private, no-store, max-age=0, CDN-specific no-store headers, Vary: * and X-Robots-Tag: noindex, nofollow. IAP authenticates the user in front of Cloud Run. The origin still verifies the signed x-goog-iap-jwt-assertion header on every request in access.rs, against the exact audience /projects/NUMBER/locations/REGION/services/NAME. That is the direct Cloud Run signed-header audience, not an OAuth client ID or URL. It does not trust the signature-free x-goog-authenticated-user-* headers, and it does not let IAP’s presence stand in for verification. When a key refresh fails, cached keys are not used, so the request is denied.

Missing or invalid assertions return 403. A staging process with a missing or malformed audience refuses to start. Cloudflare Access variables, headers and service tokens authorize nothing. An optional separate loopback-only probe listener serves no site content. Local tests prove this application boundary with a public test-only key. They do not prove a deployed IAP configuration; member, nonmember and direct-origin checks are deployment checks.

Physician entry point

Production configures no physician upstream. Configuring one there requires qualified production physician authentication first; production must not expose unconfigured proof-token delivery.

The proxy must preserve physician bearer authorization, query strings and streamed responses without forwarding browser cookies, caller-supplied service credentials or IAP identity assertions to the upstream. Upstream IAP authentication is a separate service-account credential in Proxy-Authorization, not a replacement for the physician Authorization header. The public origin’s verified IAP gate remains mandatory for all staging proxy requests. Missing service credentials or failed refreshes fail closed; neither IAP boundary may be disabled to make the proxy work.

The credential flow is keyless: IAM Credentials signJwt, using the public-site runtime identity, a short-lived JWT scoped to the configured physician origin, and a self-scoped signing permission. The custom role publicSitePhysicianProxySigner (iam.serviceAccounts.signJwt only) is bound runtime-to-itself; the staging admin bootstrap’s --physician-proxy flag creates it. This permission is identity-signing authority, not an IAM restriction to one audience. The physician infrastructure owner grants that runtime identity IAP access to only the physician service through its authoritative physician_proxy_invokers binding; public-site infrastructure does not compete with that binding. No service-account private key or token belongs in source, URLs, browser state or logs.

/physician/ is not a browser security boundary: marketing scripts on the same origin can access the physician session stored in local storage. The entire origin must therefore be treated as trusted physician-session code. Proxy responses must never enter public or CDN caches. Cloud Run streams are finite; clients reconnect rather than relying on a longer request timeout.

Image

crates/public-site/Dockerfile builds a static x86_64-unknown-linux-musl binary and copies it into distroless static Debian 12 as UID/GID 65532. Builder/runtime images are digest-pinned, Cargo uses --locked, and no mutable OS package installation occurs during the build. Only workspace manifests/crates are copied, not reference submodules, local credentials, or Terraform state. The binary is checked for a dynamic ELF interpreter during the build. Pinned inputs improve repeatability; bit-for-bit image reproducibility is not claimed without a repeated-build comparison.

The server embeds assets/, including the motion script /homepage/site.js, so docker build alone produces the complete site; there is no separate motion build.

The site reads no secrets, so it has no Doppler config, token or Secret Manager access. Cloud Run runs the image’s own /public-site entrypoint, exactly as the local smoke tests do, with the deployment-controlled environment values above set directly. The dedicated service account has no database, physician or secret access.

Infrastructure: staging IAP, production load balancer

infra/gcp/public-site is an isolated OpenTofu root. It owns public-site staging and production state through a partial GCS backend, one file per environment (see Staging state and deployment and Production state and deployment). Both environments get a separate Cloud Run service and a dedicated service account. The root creates no DNS records, project, API enablement, service identity, Google Group, database, or physician runtime dependency. Production’s one certificate is the Certificate Manager certificate described below. Its scaling defaults are bounded configuration, not demonstrated load capacity. Startup uses a TCP probe on port 8080 rather than an unauthenticated HTTP health route.

Staging (environment = "staging", the default) uses direct Cloud Run IAP and no load balancer:

  • iap_enabled = true, ingress INGRESS_TRAFFIC_ALL, the run.app URL enabled (output staging_url) and invoker_iam_disabled = false.
  • The only roles/run.invoker member is the project’s IAP service agent, service-PROJECT_NUMBER@gcp-sa-iap.iam.gserviceaccount.com. It is set through an authoritative binding on this service only. There is no allUsers grant, and CI or deployer identities get no implicit website access.
  • The only roles/iap.httpsResourceAccessor member is group:gcp-engineering@codahealth.ai (variable iap_group). This is also an authoritative binding on this service only, not a project or domain grant.
  • PUBLIC_SITE_IAP_AUDIENCE comes from project_number, region and the service name, and it is set directly on the container. The output iap_audience exposes the same value.
  • staging_domain optionally maps a verified hostname to this same service. env/staging.tfvars sets it to staging.codahealth.ai. Cloud Run manages TLS; the Cloudflare staging record is a DNS-only CNAME to ghs.googlehosted.com, as staging_domain_records returns. Native IAP remains the access owner on both hostnames.

Production (environment = "production") serves the same image behind a load balancer. Ingress is INGRESS_TRAFFIC_INTERNAL_LOAD_BALANCER and the run.app URI is disabled. It uses a serverless NEG, a global external managed HTTPS load balancer, an HTTP frontend on the same address that answers every request with a 308 to HTTPS (host, path and query kept), a MODERN / TLS 1.2 policy, Cloud CDN, and the Cloud Run invoker check turned off (invoker_iam_disabled), because the ALB does not authenticate and the organization’s domain restriction forbids an allUsers grant; ALB-only ingress and the disabled run.app URL are the boundary. TLS comes from one Google-managed Certificate Manager certificate for domains (apex and www), attached through a certificate map with an entry per hostname. It is authorized by the DNS records the certificate_dns_records output lists, not by serving traffic, and those records also renew it. Production without domains is rejected. IAP is off. No Cloud Run custom-domain mapping is created for production.

Cloud CDN and staging safety

IAP and Cloud CDN cannot be enabled together on one backend. That is one reason staging uses direct Cloud Run IAP with no backend service.

  • Production: Cloud CDN is enabled with USE_ORIGIN_HEADERS, no forced caching and no negative caching. The server emits the cache headers described above; the infrastructure does not manufacture application cacheability.
  • Staging: there is no load balancer or Cloud CDN, and no variable can add them. Origin responses are no-store, so no upstream layer may cache protected content. There is no Cloudflare dependency.

  • State. backend "gcs" {} is partial. backend/staging.gcs.tfbackend selects a dedicated staging bucket. Staging state never lives in a coda-health-prod bucket, so the CI deployer needs no production-project IAM.
  • Inputs. env/staging.tfvars holds the non-secret staging inputs: the last operator-reviewed image digest in the private public-site repository, release SHA, and physician_app_url, the physician preview service in coda-rust-staging behind its own IAP. CI deploy on push to main

The deploy-public-site-staging job in .github/workflows/ci.yml redeploys staging from pushes to main selected for full validation, after CI result passes. Engineering-skills/docs-only pushes skip deployment. It runs only when the repository variable PUBLIC_SITE_STAGING_DEPLOY is enabled; unset it to stop deploys without editing the workflow. The GitHub staging environment allows only the main branch to deploy, which matches the provider’s attribute condition. The job:

  1. Builds crates/public-site/Dockerfile with the private base-image defaults and runs smoke.py on the result.
  2. Pushes the image to public-site/public-site:<sha>. Tags are immutable, so a rerun of the same commit reuses the digest it already published.
  3. Runs tofu plan with env/staging.tfvars plus -var image=<digest> and -var release_sha=<sha>, and fails unless the saved plan is empty or an in-place update of google_cloud_run_v2_service.site alone. Then it applies that saved plan.
  4. Requires the latest revision to be Ready, serve 100% of traffic and report the new digest. It also requires anonymous requests to the run.app homepage and /health and to staging.codahealth.ai to redirect to Google sign-in.

CI and deployment identities have no website-access grant, so the job checks only that anonymous requests are sent to sign-in; an authenticated render is a manual check by a member of gcp-engineering@codahealth.ai.

env/staging.tfvars keeps the last operator-reviewed digest; a local plan run from it after a CI deploy shows the image going back. Pass the current digest with -var image=... (read it from gcloud run services describe) when planning by hand. A plan that changes anything beyond the service, such as IAM or the domain mapping, stops at the CI guard and needs an operator apply from a reviewed saved plan.

Production state and deployment

Production serves the image staging tested, without sign-in, at codahealth.ai and www.codahealth.ai from coda-health-prod. Operator applies and DNS changes require explicit operator authorization.

Promotion

promote-public-site.yml is manual (workflow_dispatch on main, input release_sha) and runs in the production environment. Starting a run is the approval: anyone with write access to the repository can promote a commit staging already built and tested. It:

  1. requires a full SHA that is on main and a successful “Deploy public site to staging” job for that push, so the image was deployed and verified on staging, not only built. Skills/docs-only pushes skip that job, so promote the latest commit staging actually deployed;
  2. finds the image the staging deploy tagged with that commit (tags are immutable) and copies that digest into the production repository unchanged;
  3. plans the production root with env/production.tfvars, that image and that SHA, and fails if the plan changes anything but an in-place update of the Cloud Run service. Load balancer, certificate, IAM and identity changes are operator applies;
  4. applies the saved plan and checks the Ready revision serves the digest with all traffic;
  5. clears the CDN and waits for it to finish;
  6. pins codahealth.ai and www.codahealth.ai to the load balancer IP with curl --resolve and checks each: /api/health reports production and the SHA, the homepage sends production’s HSTS and offers no Sign in, /physician/today is 404, and plain HTTP answers 308 to the same HTTPS URL.

The CDN is cleared because its cached HTML names hashed CSS and JS the new image no longer serves, which would load unstyled pages. Clearing the CDN does not clear browsers, so a returning visitor may see one unstyled load before the next load is current.

Synthetic patients

The patient bank is a set of fictional adult patients of one primary-care practice, each a longitudinal chart in FHIR R4. Coda runs against them where it needs realistic patients. Nothing in it is real patient data, and no physician has reviewed it.

Where the patients come from

  • The people: synthetic_hospital (benchmark_v1.3.db, MIT, fully synthetic). Each of its 1,020 adult patients is the source of one patient in the practice. Because they are in the bank, Coda is never evaluated on synthetic_hospital’s own benchmark.
  • The method: coda-gym’s. A chart is written from a requirements file that says what it may hold, so every clinical fact comes from the source or a listed addition, and nothing is invented.
  • Lab labels and reference ranges: coda-gym’s lab_reference_ranges.xlsx.
  • The format: FHIR R4 as render.rs builds it, with its MRN system and note header, and the catalog’s code systems.

What a chart is

The practice is a membership internal medicine practice in western Massachusetts, and its today is 2026-08-27 12:00 Eastern. Each source becomes the primary-care chart the same person would have there:

  • What the source says stays: its diagnoses, medications, results and events, rare ones included. Its internal and family medicine visits become the practice’s own; specialist, emergency and hospital care arrives as outside records, and how complete those records are varies by patient.
  • The practice adds what primary care does over the years: regular visits, preventive care, medication management, labs over time, notes in its own voice and visits booked after today.
  • A source diagnosis with no treatment gets its standard care. After the source ends, the patient follows the ordinary course, with no new diagnoses.
  • Dates move so the history ends before today.
  • How long ago the practice last saw the patient varies as in a real panel, from weeks to years. Outside records that arrive after that visit are filed but not reconciled, and only some patients have a visit booked.
  • A source who cannot be a living primary-care patient has no chart.

Vitals, lab values and calculated results are made by code from the patient’s state, never typed by an author.

Observability

The observability stack has selectable operations destinations (traces, logs, metrics, alerts) and Langfuse for agent runs. Destinations are Datadog (APM, logs, Error Tracking, monitors), a self-hosted Grafana stack (Tempo, Loki, Prometheus, Grafana). Both use the same OpenTelemetry trace. The operations backend gets every span with agent content removed. Langfuse gets only model generations, in the hosted project at https://hipaa.cloud.langfuse.com, which Langfuse’s BAA covers. The collector strips content from the operations pipelines unconditionally, so no content depends on an operations vendor’s BAA scope.

This page describes configuration and verification, not live deployment status. Infrastructure, Datadog and Grafana changes require separately authorized, reviewed plans; the observability operator owns their application.

Per signal:

Sidecar lifecycle and outages

The sidecar is a second container in each Cloud Run service. The product container does not depend on it: Cloud Run starts and health-checks the product on its own probes, and the sidecar has its own startup probe on the collector’s health_check port with 1 vCPU and 256 MiB limits. Startup order is independent, but revision readiness is not: a collector image-pull or startup failure can prevent the new revision from serving.

  • Gateway or backend outage. The sidecar keeps a bounded in-memory queue and retries for a bounded time, then drops. The product never blocks on export, and its requests keep succeeding.
  • Sidecar crash. The product’s exporter fails fast against localhost and drops; Cloud Run restarts the sidecar. Telemetry from that window is lost.
  • CPU and shutdown. Enabling observability disables CPU throttling for the product and sidecar so export can drain between requests. Both containers receive 1 vCPU, increasing per-instance allocation and billing. This cost belongs in the reviewed deployment plan. On scale-in, the product makes a bounded flush through TelemetryGuard and the sidecar flushes on SIGTERM within Cloud Run’s 10-second grace period; remaining queued telemetry is lost.

Working-window timing

The shared harness retains the opening time in Unix milliseconds on each WindowOpened event, alongside its reason and optional note reference. ProviderStarted retains the request’s admission time. Products store both in their existing run journals. These wall-clock timestamps let inspection relate a window opening to surrounding requests without a second timing store. Cross-process comparisons depend on the hosts’ clock synchronization. The records contain model context and stay with the product; they are not exported to Datadog as raw logs.

  1. Open the primary Datadog notification from the confirmed alert_notify destination. Grafana evaluates equivalent operational rules in shadow mode; it does not send service notifications. HTTP failures and latency cover service requests; asynchronous worker failures need a separate signal because the originating request can already have succeeded.
  2. Follow the error log’s trace link. The worker attempt and generation spans carry canonical correlation; a broker message ID identifies a delivery, not an attempt. Copy coda.run_id, coda.work_id, any predecessor ID, and the trace ID. Preserve the query window and release version with the evidence.     • Rates and latency. Prometheus traces_spanmetrics_* series by service; exemplars open the matching traces.
  3. An authorized product operator reads back the matching persisted attempt from physician Postgres, scoped to the intended practice and physician. Chat attempts are in the state.attempts collection of physician_runtime_conversations; current reply-revision attempts are in physician_runtime_reply_drafts, and earlier accepted revisions are archived in physician_runtime_reply_revisions. Private Nix binary cache

infra/gcp/nix-cache owns an isolated private GCS bucket and bucket-scoped reader/writer identities. Select its project and remote-state backend explicitly; apply only an operator-approved saved plan. It does not own product deployment permissions. Nix uses GCS’s S3 interoperability endpoint, so its HMAC credentials are distinct from the WIF credentials used by deploy jobs.

Keep HMAC and signing secrets in Doppler, outside OpenTofu state. Deliver the reader credentials to CI separately from the writer credentials. The reader HMAC pair is a repository secret, because every Nix job reads the cache and most run outside any environment; it grants only object reads on this bucket. The GitHub nix-cache-write environment must restrict deployment branches to main before installing any writer or signing secrets. Never put those secrets at repository scope: a workflow condition alone cannot protect secrets from edited PR code. Only the nix-cache-publish job enters nix-cache-write. It runs on a main push after images passes, rebuilds the allowlisted roots from the cache, and uploads them. images itself holds no cache-writer secrets on any event. Changing cache trust or rotating its signing key requires operator review. Publishers share the nix-cache-main-writer concurrency group because create-only object permissions cannot safely handle simultaneous uploads of the same object. An active publisher is not cancelled; GitHub may replace an older pending one with a newer one, whose closure supersedes it. The image proofs, CI result and deployments stay outside that group and do not wait for publication, so a burst of merges cannot cancel them. Any additional publisher must use the same serialization policy rather than weakening the bucket permissions.

The cache retains compiled dependency artifacts as well as application outputs; final image closures alone do not retain the intermediate Rust compilation work. Native server, WebAssembly and patient-bank builds keep separate dependency artifacts in nix/packages.nix. Cache reads preserve Nix’s signature verification and the upstream substituter. A cache miss or outage must still run the build and all image proofs. Disabling NIX_CACHE_ENABLED restores the uncached workflow without changing the proof commands.

The cache contains private build inputs and outputs. Do not make the bucket public or copy credentials into the Nix store. Object-age deletion is not a safe cache garbage collector: deleting a NAR while retaining its metadata or references can break substitution. Retention changes must account for the reference graph.

Local cache warming with act

The local workflow builds the same allowlisted roots as the hosted writer: three dependency artifacts, six runtime, migration and job images, and the three dev shells CI enters (agent, release, observability). It only warms the binary cache; it does not load or push images, deploy services, or replace the hosted image proofs. Hosted publication remains a protected main-push operation. Local publication is an explicit operator-authorized exception for a reviewed, full commit SHA. Serialize it with every other writer: do not run it while a hosted or another local publication is active. act does not participate in GitHub’s writer concurrency group.

Use a clean, standalone checkout containing the reviewed commit, not a linked worktree: act copies files into the container, and a worktree’s .git file points outside that copy. The reader copies the server-dependency closure into an empty disposable store from the private cache alone, without builds, and verifies contents and trust. All temporary credential files and the reader store are removed on normal failure or completion; act --rm also removes the job container on failure. Abrupt host termination can require removing that specific stopped act container/volume; do not prune unrelated Docker resources.

The helper reports stages, elapsed heartbeats, exit codes, and fixed error categories without printing raw SDK output. A heartbeat means the process is alive, not that an object was uploaded. It seeds repeated NAR content before the parallel copy to avoid create-only HEAD/PUT races within one publisher. This does not make multiple publishers safe. Unknown errors remain withheld; reproduce with synthetic local transport credentials rather than enabling verbose real-secret logs. Failures are fatal locally. No cache credentials are needed for list, dry-run, checkout verification, installation, or building from the upstream cache.

Telemetry sidecars and CPU allocation

With observability_enabled, each service runs an otel-collector sidecar (1 vCPU, 256 MiB) that forwards to the observability gateway. The sidecar does not change how CPU is allocated:

Servicecpu_idleMinimum instancesWhy
physicianfalse0Its Postgres authority listener and Redis subscriber run between requests while an instance is up; the worker owns accepted turns, so none has to stay up
duettrue0All work happens inside a request
physician-workerfalse1Its Postgres listener, 10 s poll and lease renewals run outside any request

Telemetry is best effort, as the sidecar’s own configuration states. Under request-based CPU, a batch queued after the last response waits until the next request or until shutdown, when Cloud Run gives the instance CPU again. At shutdown, Cloud Run sends SIGTERM to the product and the sidecar together, so the product’s final flush can race the collector’s own exit. The collector’s queue is bounded and drops on overflow, and its retries give up after 5 s. Telemetry still queued in either process when the instance stops is lost. Services never wait on it.

Cost at Cloud Run tier-1 prices ($0.000018 per vCPU-second, $0.000002 per GiB-second, instance-based) for an instance kept warm for a month:

  • physician with the sidecar: 2 vCPU and 1.25 GiB, about $101 a month instead of about $53 without it, for each instance kept up all month. It scales to zero, so it bills only while an instance is up, including up to 15 idle minutes after its last request.
  • physician-worker has the same shape, instance-based CPU and its own minimum instance, so it is kept warm all month as well.
  • duet stays on request-based billing and scales to zero, so idle time costs nothing. Instance-based CPU would have billed each warm instance for up to 15 idle minutes after every request, up to about $101 a month at continuous low traffic.

  • Physician WAL archiving and disk backpressure (physician_sql_wal_archive_failed, physician_sql_disk_pressure). coda/physician_sql_wal_archive_failed matches archive command failed and archiving write-ahead log file .* failed in rust-physician’s cloudsql.googleapis.com/postgres.log and pages on the first failed archive cycle so low-traffic 5-minute archive_timeout cycles notify before 15 minutes of committed data are unarchived. physician_sql_disk_pressure alerts when rust-physician exceeds 0.85 disk utilization for 10 minutes from local pg_wal accumulation.
  • Cloud SQL PITR lag metric boundary. Google Cloud SQL (cloudsql.googleapis.com) exposes no Cloud Monitoring metric for point-in-time recovery-point age, latest recoverable timestamp, or silent asynchronous WAL offload lag into Google-managed Cloud Storage (write_ahead_log/*_bytes_count tracks local WAL flush and sits at zero when idle; bytes_used_by_data_type tracks stored bytes rather than lag; replication/replica_byte_lag exists only on read replicas). Automated alerts therefore catch daily backup failures or >26-hour absence, PostgreSQL archive_command failures, and pg_wal disk pressure, while actual recovery-point lag against the 5-minute target and 15-minute limit is measured only through isolated point-in-time clone rehearsals.

Disposable database recovery rehearsal

workspace-tools staging-restore is an operator command, not part of automatic deployment. It accepts only the canonical staging physician or Duet source, a successful backup and a fresh rust-restore-<product>-<run> target. Its default is read-only cloud preflight; cloud writes require both explicit execution and authorization flags. The operator must separately authorize the billable target and cleanup. The normal release identity receives no SQL administration privileges.

Run cargo run -p workspace-tools -- staging-restore --help for the command interface. Use a fresh receipt path for execution after preflight. The command creates a private PostgreSQL target sized from the source’s data disk (preflight refuses sources outside 10-50 GB), records its creation identity, restores the selected backup and waits for bounded operations. It refuses an existing target rather than trusting its name or labels. Receipts retain operation IDs, backup age, elapsed restore time and cleanup state; an interrupted create may leave a billable resource whose identity requires manual investigation. Never blindly retry or delete a target solely by its name.

When cleanup refuses because the receipt has no target_created_at (the create failed or timed out before its identity was recorded), the authorizing operator owns the investigation. Describe the receipt’s create_operation, then describe the instance and match its coda-run label to the receipt’s run_id, and its project, network and create time to the receipt. Delete it only under a separate explicit authorization, and record the result beside the receipt.

Cloud restore completion is explicitly unqualified. Before a rehearsal:

  1. Establish synthetic sentinel records through each product’s existing owners and record their identities without clinical content in the evidence bundle. Select a successful backup containing them. For Duet, retain independent privacy receipts for a deletion/withdrawal accepted after that backup.
  2. Review the target resources and operator access. Keep restored databases out of service routing, workers, subscriptions and outbound effects. Do not reuse a managed staging or production instance as a restore target.
  3. Restore each product separately. Through an isolated validation process, check the owning migration ledger, synthetic saved-state readback and runtime versus migrator permissions. Run Duet’s complete independent journal replay and check deletion/withdrawal refusal as described in privacy recovery.
  4. Record validation commands/results beside the cloud receipt, tied to the target and revision. Record measured recovery duration and recovery-point age against the backup policy; retention settings alone do not establish measured RPO or RTO. For physician PITR measurement, clone rust-physician with gcloud sql instances clone ... --point-in-time into a fresh private rust-restore-physician-pitr-<run> instance that is never attached to serving, workers, queues or external channels, verify the sentinel record timestamp, and clear the clone’s inherited deletion protection only under the separate cleanup authorization for that exact disposable target.
  5. After separate cleanup authorization, use the receipt-bound cleanup command. It checks project, creation identity, private network and drill labels before deleting only its disposable target. Record deletion completion; unresolved or uncertain creation/deletion remains an operating obligation.

Neither local Postgres recovery tests nor mocked cloud operations replace an actual authorized Cloud SQL restore and product readback. Keep those proof types separate in the release handoff. Do not reopen serving based only on a successful cloud operation or a manually asserted status.

Operating limits and failure investigation

The environment root owns resource bounds, not an aggregate spending ceiling. Its runtime and worker instance caps apply per revision, so overlapping revisions can consume more than one revision’s cap. CPU, memory, request concurrency and timeouts bound individual executions; migration jobs have one task, a 600-second timeout and no automatic retries. SQL disk growth is capped and backups/PITR are retained for seven days. Redis, SQL, minimum instances and networking can incur charges while no requests run.

On coda.dabney.moe and staging Cloud Run services, physician-sample, duet-api, and public-site share one HTTP ingress abuse boundary in ingress.rs (IngressGuard). It enforces fixed-window per-client IP rate limits (429 Too Many Requests with Retry-After and Cache-Control: no-store) keyed from the rightmost trusted X-Forwarded-For hop, strictly tightens quotas on unauthenticated auth/magic-link/OTP/invite/sync paths, rejects oversized bodies fast (413 Payload Too Large + DefaultBodyLimit), bounds concurrent in-flight non-probe requests (503 Service Unavailable), caps tracked client buckets in memory, and exempts health/readiness probes (/health, /healthz, /readyz, /api/health). Runtime knobs are CODA_RATE_LIMIT_RPM, CODA_AUTH_RATE_LIMIT_RPM, CODA_MAX_REQUEST_BODY_BYTES, CODA_MAX_CONCURRENT_REQUESTS, CODA_TRUSTED_PROXY_HOPS, and CODA_RATE_LIMIT_ENFORCE_LOOPBACK (automatically enforced when K_SERVICE, CODA_HOSTED, APP_ENV, or CODA_ENVIRONMENT is set, exempting local loopback tests otherwise).

Before a rehearsal, compare the deployed Cloud Run services/jobs, SQL settings and worker settings with the reviewed root inputs. Record identifiers and nonsecret limits, not full service descriptions containing environment values. Have the billing administrator verify the project budget’s thresholds and notification recipients, and the model-provider owner verify account limits. A budget alert is not a hard cap; a per-turn bound is not an aggregate provider limit. Record inaccessible settings as unverified rather than treating them as absent or effective. Changes to budgets, IAM or capacity need their owners’ authorization.

For a failed release, start with its workflow run and release receipt. Use the recorded execution name to find migration logs, and the recorded revision names to find runtime/worker logs. Inspect current traffic independently before a retry. Do not copy raw environment values, tokens or clinical content into a receipt or public diagnostic. For worker failures also read the attempts saved on the turn in physician_runtime_conversations: each failed attempt is recorded there with its time, and a turn that failed five times stays failed until the physician chooses Try again. A deployment check and a ready process do not establish that a clinical journey succeeded.

Physician scaling (Redis fan-out and the chat-turn worker)

enable_physician_scale lets the physician site run on more than one instance. It takes effect only together with enable_workloads. Applying it writes project IAM bindings that engineering can’t write alone. Everything it creates belongs to physician; Duet gets no cache, worker, grant or setting, and the root’s tests check this. No Pub/Sub topic, subscription or push identity exists, and the root does not enable the Pub/Sub API: turns are announced and claimed in Postgres, as the physician site chapter describes.

  • cache.tf creates the Memorystore instance rust-physician-cache: Basic tier, 1 GB, Redis 7.2, AUTH and TLS (SERVER_AUTHENTICATION). It sits on the existing rust-sql-private peering, so it has no public endpoint. It carries workspace_changed and workspace_settled between instances. Clients use fred with TLS and AUTH (PHYSICIAN_REDIS_URL, PHYSICIAN_REDIS_CA_PEM). Lag or a reconnect is a resync, and the page refetches. Sign-in and panel notices stay on the Postgres physician_authority triggers.
  • workloads.tf adds the physician-worker Cloud Run service. It has internal ingress and no IAP, IAM invoker checks stay on, and only the availability probe may invoke it: nothing pushes work to it, and its only HTTP surface is the readiness probe. The worker runs as physician-worker-runtime, which may reach only the physician SQL instance. It reads the physician-runtime-doppler-token slot and runs on stg_physician_runtime, because it needs exactly those secrets; a second token on the same config would add a rotation step without narrowing anything. It has cpu_idle = false and one minimum instance, because no request carries its work. It listens on Postgres for accepted turns, reads the due work every 10 s, claims the leased turn, runs the model, commits, and publishes workspace_changed. A turn whose worker died is taken again when its lease runs out, so recovery belongs to the worker. Every minute each worker instance also writes the queue gauges the worker monitors read, which is why its identity holds roles/monitoring.metricWriter.
  • The physician site gets PHYSICIAN_DURABLE_CHAT=1 and cpu_idle = false, and scales to zero like Duet. PHYSICIAN_DURABLE_CHAT=1 is what hands turns to the worker. CPU stays allocated because its Postgres listener and Redis subscriber must keep running between requests. Its hourly receipt compaction sweeps once when each instance starts and needs no warm instance. Duet keeps cpu_idle = true. runtime_environment may not set any of the scaling keys, and Duet may not set any PHYSICIAN_* key.

PHYSICIAN_REDIS_URL embeds the AUTH string, so it lives only in Doppler, as does PHYSICIAN_REDIS_CA_PEM. Neither value is committed.

Connection budget

The physician site and physician-worker both connect as the physician-runtime role, whose CONNECTION LIMIT is 40 (bootstrap-grants.sql). Each process opens one Postgres pool, local_product::runtime::Store::connect, and every store in it reads through that pool: the runtime store, auth, the front door and /readyz. The pool holds at most MAX_CONNECTIONS = 3 connections, waits up to 10 s for one, and closes a connection idle for 60 s. It keeps a returned connection only outside any transaction, so a request cancelled mid-transaction leaves nothing open for the next one. Each process’s long-lived LISTEN (the site’s authority feed, the worker’s wakeups) holds one of those 3 while it runs, so two remain for requests and claims.

A rolling deploy runs the old and new revision side by side, so the peak is

peak = services × max_instances × overlapping revisions × MAX_CONNECTIONS
     = 2 × 2 × 2 × 3 = 24 of 40

with max_instances at its default of 2. That leaves 16 for the migration job and operators, and keeps the peak at or below 30. The highest max_instances the role fits is 40 ÷ (2 × 2 × 3), rounded down: 3. Raising max_instances past it, or raising MAX_CONNECTIONS, needs this budget redone and the role limit changed with it.

To turn scaling on:

  1. Deploy the code first. The site that queues turns and physician-worker must be on main with a successful Deploy staging job. Skills/docs-only pushes skip that job, so overall CI success is not deployment evidence. The plan refuses to run without a digest in images.physician.worker.
  2. Decide who applies. The plan creates bindings group:gcp-engineering@codahealth.ai cannot write: the worker’s project-level Cloud SQL and Monitoring metric-writer roles. Apply as the project Owner, or grant engineering Project IAM Admin conditioned on api.getAttribute('iam.googleapis.com/modifiedGrantsByRole', []).hasOnly(['roles/cloudsql.client', 'roles/cloudsql.instanceUser', 'roles/monitoring.metricWriter']), and remove it afterwards. Do not apply part of the plan.
  3. Plan, review, apply. Use the saved-plan procedure right before applying, because a saved plan goes stale once deploy-staging or another apply touches state. A scaling-only plan must not change Duet or destroy anything. Apply exactly the reviewed file.
  4. Write Redis into Doppler and start new revisions, with the commands below. OpenTofu doesn’t write these two values. Without them each process keeps an in-process bus, so the worker’s events never reach the site. Runtimes read Doppler only at process start. The AUTH string goes straight into Doppler and never reaches the screen, argv or a file.
  5. Verify. Open site tabs until labels.instanceId in the physician stream logs shows two instances, send a turn from one tab, and check the reply appears in a tab on the other instance. The turn’s row in physician_runtime_conversations should show one completed attempt.

Shared mail service

Products hosted outside the Rust VPC can use the mail-relay binary in crates/gmail. The mail-only production root owns its separate deployment in coda-health-prod; rust-environments continues to own staging. It wraps the existing SmtpRelay; it does not own product sign-in, message templates, recipients, send records or retry decisions. The physician server continues to use that same transport directly. There is one SMTP implementation and no additional mail vendor, mailbox credential, queue or persistence layer.

Build crates/gmail/Dockerfile from the workspace root for linux/amd64. It follows the existing private, digest-pinned base-image convention and builds only cargo build --locked --release -p gmail --bin mail-relay. Build/push and infrastructure apply require the normal release approvals. Configure its reviewed image digest explicitly.

In infra/gcp/rust-environments, mail_relay_image defaults to null (no service). Setting a reviewed digest and nonempty mail_relay_invokers creates an IAM-protected Cloud Run service, a runtime identity with no application-data roles, and a service-scoped invoker binding. enable_physician_smtp_relay must already be enabled: the adapter uses that existing network, subnet and NAT address, preserving the Workspace IP allowlist. It needs no Doppler token. Runtime settings are MAIL_FROM=signin@codahealth.ai, MAIL_NOTIFICATION_FROM=notifications@codahealth.ai (the binary default), and MAIL_LISTEN_ADDR=0.0.0.0:8080.

For Gym staging, the named caller is serviceAccount:workspace-web-staging@coda-gym.iam.gserviceaccount.com. Production uses serviceAccount:workspace-web@coda-gym.iam.gserviceaccount.com on its own relay and authorized egress, managed by infra/gcp/shared-mail in a separate state. Production must not be planned or applied from the Rust staging root. Neither root grants a public invoker or routes production through staging. The mail_relay_url output is both the caller’s base URL and ID-token audience. Cloud Run IAM checks identity; the adapter does not add a second token verifier.

POST /send accepts JSON {purpose, to, subject, text, html?}. purpose is signin or notification; the service maps it to its two configured identities. Callers cannot supply an arbitrary From address. Omitted purpose uses the sign-in sender; unknown purposes are refused before SMTP. HTTP 204 means the SMTP server accepted the message, not that a mailbox received it. HTTP 422 means invalid headers or an explicit SMTP refusal. HTTP 503 means acceptance could not be established; a caller must not assume it is safe to retry. No message content, code, bearer token or SMTP response text is returned or logged by the adapter. GET /readyz returning 204 checks only process readiness, not SMTP or delivery. Gym owns its cutover and cleanup steps in authoring/web/infra/README.md in the coda-gym repository.
